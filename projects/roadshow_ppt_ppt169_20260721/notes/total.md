# 01_cover

评委老师好，我们组的产品叫三会智理，它是一个面向上市企业会议管理的网页应用，专门服务股东会、董事会和监事会（也就是“三会”），以及其他会议的日常管理工作。在许多公司尤其是待上市公司中，以三会为主的会务工作对企业负担较重。从规划到记录的全过程繁琐、合规风险高。法务和董秘需要核对通知期限、要整理与会人员名单和会议纪要，还要准备全套通知、议程、签到表、决议等文书，最后归档留存。这些工作大量依赖人工，且容错率非常低，合规瑕疵就意味着法律风险和经济损失。三会智理旨在将整套流程自动化，并且预测合规风险供用户调整会议安排、修改会议文书。

# 02_overview

三会智理是一个全栈网页应用，前端用React构建界面，后端用Express提供接口，两者部署在同一个服务里，可以直接在云平台上运行。系统选择飞书多维表格作为数据中台，意味着会议信息、人员信息、议案、文书等数据不是孤立地存在于我们自己的数据库中，而是实时读写在客户的飞书表格中，方便企业的其他系统和人员协同查看。打开网页，第一个板块是全局控制台，待办会议数、已生成文书数、法定通知预警、与会人员总数四个核心指标在最醒目的位置，配合按会议类型着色的日历视图，让用户对于临期会议、合规指数较低的会议一目了然。

# 03_meeting

会议管理模块负责会议的创建和维护。创建会议时，系统会根据选择的会议类型自动提示对应的法定门槛，比如临时股东会需要持股10%以上的股东提议才能召开，这类规则直接写进了创建流程中。与会人员的选择也做了优先级排序，董事、监事、高管、股东依次排列，股东还会自动标注持股比例。会议信息保存后实时同步到飞书表格，如果飞书那边还没有对应字段，系统会友好地提示并把数据先存在本地。
会议结束后，录音工作台负责将音频与会议纪要转成规范文档。它支持上传文稿与录音文件，后者使用飞书妙记的转写功能。转写完成后，系统能把飞书里该会议的基本信息、录音识别文件和已有议案自动关联，明确标出待补齐的内容。生成的文本可以按照国标文档规范预览和编辑，最后一键导出成Word文件，也可以推送到文书中心继续加工。

# 04_docs

文书中心是承担核心产出的模块。它提供会议通知、议程、签到表、决议、纪要、公告等多种文书模板，支持在线编辑和实时预览，最终可以导出成Word或PDF。这个模块和会议管理、录音工作台双向联动。系统在服务端准备了一整套Word模板，可以直接用飞书里的会议数据批量渲染，把一场会议需要的全部文书打包成压缩包下载，股东会对应9份文书，董事会和监事会各对应6份。
与会人员模块管理董监高和股东的完整信息，包括任期、独立性声明、关联关系、持股比例。这个模块也做了自动化的合规检测：比如系统规定董事和高级管理人员不能兼任监事；独立董事占比会自动计算并和监管要求的33%比较；每个人的任期兼剩余天数也会自动标注。

# 05_compliance

这里我想重点讲一下合规审查模块，这是我们认为最能体现产品价值的部分。在合规场景中，AI最大的风险是信息准确度不足，轻度的法律风险也可能造成极大损失。因此，我们在合规审查上设计了两条通道。第一条通道基于大模型做自由文本分析，生成一份可读性强的综合报告。第二条通道，是一个不依赖大模型的规则引擎。它从上传的文件和飞书里的会议上下文中，用规则化的方式提取事实，然后逐条对照公司法的具体条款生成风险项，并给出一个0到100的合规指数。该引擎的设计原则是只依据当前材料下结论，如果某项信息缺失，就明确标注为“无法判断”。审查结论必须可回溯，每一条风险评价都能追溯到具体的规则和事实，而不是一个黑箱式的评分。推理链条完全透明。

# 06_tech

从实现的角度看，整个系统是一个前后端运行在同一进程里的 Express 应用：浏览器端的 React 单页应用直接向后端接口发起请求，同时保留一部分纯前端能力，比如用 docx.js 在浏览器端直接生成 Word 文件。后端的核心是飞书接入这一层，负责获取和缓存访问令牌、读写多维表格记录，这一层做了容错设计：默认按表名自动匹配，也支持用环境变量手动指定。外部集成方面，飞书多维表格和妙记是系统的主数据源，签名认证部分是自行实现的HMAC-SHA256签名算法。文书批量生成模块在服务端用JSZip读取预先准备好的Word母版文件做占位符替换和循环展开。
