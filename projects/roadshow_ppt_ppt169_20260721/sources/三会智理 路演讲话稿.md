# 开头

评委老师好，我们组的产品叫三会智理，它是一个面向上市企业会议管理的网页应用，专门服务股东会、董事会和监事会（也就是“三会”），以及其他会议的日常管理工作。

在许多公司尤其是待上市公司中，以三会为主的会务工作对企业负担较重。从规划到记录的全过程繁琐、合规风险高。法务和董秘需要核对通知期限、要整理与会人员名单和会议纪要，还要准备全套通知、议程、签到表、决议等文书，最后归档留存。这些工作大量依赖人工，且容错率非常低，合规瑕疵就意味着法律风险和经济损失。三会智理旨在将整套流程自动化，并且预测合规风险供用户调整会议安排、修改会议文书。

# 产品概述

三会智理是一个全栈网页应用，前端用React构建界面，后端用Express提供接口，两者部署在同一个服务里，可以直接在云平台上运行。系统选择飞书多维表格作为数据中台，意味着会议信息、人员信息、议案、文书等数据不是孤立地存在于我们自己的数据库中，而是实时读写在客户的飞书表格中，方便企业的其他系统和人员协同查看。

打开网页，第一个板块是全局控制台，待办会议数、已生成文书数、法定通知预警、与会人员总数四个核心指标在最醒目的位置，配合按会议类型着色的日历视图，让用户对于临期会议、合规指数较低的会议一目了然。

从全局控制台往下，系统展开为几大模块，分别对应会议从筹备到归档的各个阶段。

# 会议管理

会议管理模块负责会议的创建和维护。创建会议时，系统会根据选择的会议类型自动提示对应的法定门槛，比如临时股东会需要持股10%以上的股东提议才能召开，这类规则直接写进了创建流程中，省去逐条查询核对公司法条文的工作量。与会人员的选择也做了优先级排序，董事、监事、高管、股东依次排列，股东还会自动标注持股比例。会议信息保存后实时同步到飞书表格，界面上会显示具体的同步时间，如果飞书那边还没有对应字段，系统会友好地提示并把数据先存在本地，不会因为一个字段缺失就导致整条数据丢失。

# 录音工作台

会议结束后，录音工作台负责将音频与会议纪要转成规范文档。它支持上传文稿与录音文件，后者使用飞书妙记的转写功能。转写完成后，系统能把飞书里该会议的基本信息、录音识别文件和已有议案自动关联，明确标出待补齐的内容。生成的文本可以按照国标文档规范预览和编辑：A4纸张比例、页边距、字体字号、行距都可以调整，标题、发言人、时间地点等信息会自动识别并加粗，最后一键导出成Word文件，也可以推送到文书中心继续加工。

# 文书中心

文书中心是承担核心产出的模块。它提供会议通知、议程、签到表、决议、纪要、公告等多种文书模板，支持在线编辑和实时预览，最终可以导出成Word或PDF。这个模块和会议管理、录音工作台双向联动：会议信息变化会同步过来，录音工作台生成的纪要也能一键导入。除此之外，系统在服务端准备了一整套Word模板，可以直接用飞书里的会议数据批量渲染，把一场会议需要的全部文书打包成压缩包下载，股东会对应9份文书，董事会和监事会各对应6份，这些数量是和公司法对不同会议类型的文书要求直接对应的。

# 合规审查

这里我想重点讲一下合规审查模块，这是我们认为最能体现产品价值的部分。

合规场景中，AI最大的风险是信息准确度不足，捏造法条等幻觉难以被识别，而合规业务的容错率极低，轻度的法律风险也可能造成极大损失。

因此，我们在合规审查上设计了两条通道。第一条通道基于大模型做自由文本分析，生成一份可读性强的综合报告，帮助使用者快速了解整体情况。第二条通道，也是我们更看重的一条，是一个不依赖大模型的规则引擎。它从上传的文件和飞书里的会议上下文中，用规则化的方式提取事实——公司名称、会议类型、召开日期、通知期限、出席情况、表决方式、签署情况，然后逐条对照公司法的具体条款生成风险项，标记为高风险、中风险、低风险或者提示，并给出一个0到100的合规指数。该引擎的设计原则是只依据当前材料下结论，如果某项信息缺失，就明确标注为“无法判断”。这一点我们在代码注释和实际实现上是完全一致的，也是我们认为最应该被大家关注的地方：审查结论必须可回溯，每一条风险评价都能追溯到具体的规则和事实，而不是一个黑箱式的评分。

审查过程本身也是透明的。界面上会展开完整的推理链条，从文件解析到要素提取，再到法规匹配，最后和飞书里的会议、议案、纪要字段做交叉核验，每一步都可以点开查看。审查完成后，风险点会以独立卡片的形式逐条列出，配合颜色区分严重程度，方便用户追溯。

# 与会人员

与会人员模块管理董监高和股东的完整信息，包括任期、独立性声明、关联关系、持股比例。这个模块也做了自动化的合规检测：比如系统规定董事和高级管理人员不能兼任监事，选择职位时如果违反这条规则会直接弹出警告；独立董事占比会自动计算并和监管要求的33%比较；每个人的任期兼剩余天数，并用不同颜色标注不同剩余天数。

# 技术实现

从实现的角度看，整个系统是一个前后端运行在同一进程里的 Express 应用：浏览器端的 React 单页应用直接向后端/api/\.\.\.系列接口发起请求，同时保留一部分纯前端能力，比如用 localStorage做本地缓存、用 docx\.js 在浏览器端直接生成 Word 文件，不依赖服务端往返。后端入口server\.ts里的startServer\(\)同时承担后端 API 服务和前端开发服务器两个角色，开发阶段用Vite的中间件模式挂载在同一个进程里，生产环境则改为托管构建产物dist目录下的静态文件，并对前端路由做 fallback 到index\.html。端口默认使用 3001，部署到 Render 平台时读取环境变量PORT。构建配置里还设置了路径别名、Tailwind 的 Vite插件、开发环境下对话式智能体接口的本地代理，以及适配 GitHub Pages 子路径部署的相关配置。

前端主壳App\.tsx里包含可拖拽的侧边栏、顶部的全局模糊搜索（同时匹配文书和法规内容）、基于localStorage中会议列表提前 10 天计算的日程提醒，以及用浏览器 History API 实现的前端路由。八个功能模块——仪表盘、会议管理、录音工作台、合规审查、文书中心、知识库、人员矩阵、系统设置——都是独立的页面组件，配合侧边栏和统计卡片这两个基础组件复用。业务逻辑层单独拆出了服务模块，分别负责会议的增删改查和议案生成、表决相关的读写、文书打包下载的请求封装，以及对话式智能体接口的流式调用和连接测试；工具层则封装了用 docx 库在前端直接生成表决票、制度文件等 Word 文档的逻辑，以及公司名称的规范化处理。所有领域模型——会议、语音转写片段、合规问题项、生成的文书、知识库条目、人员——都统一定义在一个类型文件里，保证前后端字段和内部各模块之间的一致性。

后端的核心是飞书接入这一层，负责获取和缓存飞书的租户访问令牌、读写多维表格记录、缓存字段名解析结果，并把人员、会议、股东、议案、文书、表决这几张表的数据统一归一化成系统内部的数据结构，同时接入飞书妙记，处理飞书自动化的回调写回。这一层做了容错设计：默认按表名自动匹配对应的飞书数据表，如果匹配不到，也支持用环境变量手动指定表格 ID，避免因为不同客户的飞书环境配置差异导致对接失败。合规审查的规则引擎是一个独立模块，不依赖大模型，基于正则和关键词从上传文本以及飞书会议上下文中提取事实——公司名称、会议类型、日期、通知期限、出席、表决、签署等，逐条对照公司法生成高、中、低、提示四级风险项，并给出一个 0 到 100 的合规指数；设计原则是只依据当前材料下结论，信息缺失就明确标注为无法判断，不替使用者编造答案，这一点在代码注释和实际实现上是完全一致的。议案自动生成用的是一个很轻量的大模型接口封装，只做 fetch 调用，没有额外依赖，调用失败时会降级到内置的示例议案，保证这个功能不会因为外部服务波动而完全不可用。文书批量生成模块在服务端用JSZip读取预先准备好的Word母版文件，做占位符替换和议案列表的循环展开，最终打包成压缩包返回，模板数量做了校验，股东会对应九份文书，董事会和监事会各对应六份。另外还有两个小模块分别负责文档正文的抽取和法规标题的自动识别。

外部集成方面，飞书多维表格和妙记是系统的主数据源，也是自动化触发的入口，飞书自动化可以带着约定的密钥调用系统的合规审查接口，触发审查并把结果写回飞书表格。录音文件的识别接入了一个语音识别服务，签名认证部分是自行实现的HMAC\-SHA256签名算法，没有使用现成的 SDK。数据和资源方面，服务端存放着按股东会、董事会、监事会三类整理好的 Word 母版文件；前端另外维护了一套二十三个的XML模板，覆盖九种会议类文书和十四种制度类文书；知识库的数据来自一个脚本，扫描本地规则目录下三百七十五份 Word、PDF 等格式的文件，抽取生成结构化的法规清单和纯文本内容，供前端加载展示。构建方面，开发和启动都通过一个脚本直接运行入口文件，构建用Vite的标准构建流程，类型检查用 TypeScript 的编译器直接跑一遍，知识库清单的生成则是一个独立的脚本命令。

# 结尾

综上所述，三会智理旨在将重复繁琐、容错率低的企业会务工作进行自动化执行和合规审查，并通过借助深度融入飞书生态提高本产品的用户间通信效率。感谢各位垂听，请各位评委老师批评指正。
